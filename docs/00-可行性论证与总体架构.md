# 应急去中心化通信平台 · 可行性论证与总体架构

> 代号建议：**ResQNet / 应急通**
> 版本：v0.1（2026-11-25）
> 定位：灾后无公网场景下，设备间自组网转发文字、语音消息与位置的信息互通平台
> 参赛赛道：2026 Qoder 高校创造力大赛 · Hack4Good 技术向善

---

## 0. 一句话结论

- **文字 + 位置 + 语音消息的多跳自组网：可行**，有成熟先例（Meshtastic、Briar、Bridgefy），工程量大但路径清楚。
- **广域（公里级）实时语音通话：在"手机 + 免执照低功率无线电"下不可行**。语音只能走两类通道：近场（WiFi/BLE，几十到几百米）或持照/商业卫星（天通、海事卫星）。
- **卫星：北斗三号短报文可以收发文字（单条约 1000 汉字），但需要北斗卡与运营资质**；不是"插上就能用"。
- **5 天比赛周期内**：能交付"协议内核 + 多节点仿真 + 可点开的 Web 指挥台（文字/SOS/位置/语音消息）"，交付不了真实多机 LoRa 语音。先把"可演示、可扩展"的骨架做对，是最不容易返工的做法。

## 1. 需求拆解（先定边界，避免后期推倒）

### 1.1 角色

| 角色 | 核心诉求 | 典型设备 |
|---|---|---|
| 受灾者 / 失联者 | 一键求救、报位置、低电量长待机 | 手机 |
| 救援队员 | 队伍内互通、看到队友位置、语音调度 | 手机 + 随身中继 |
| 现场指挥 | 全局态势图、任务下发、与外网互通 | 电脑 / 平板 / 指挥车 |
| 家属 | 查询亲人最后位置 | 有网时的 Web |
| 中继节点 | 无人值守转发 | 车载、无人机、太阳能节点 |

### 1.2 功能清单（按优先级）

| 优先级 | 功能 | 说明 |
|---|---|---|
| P0 | SOS 一键求救 | 带位置、身份、电量，最高优先级，反复重发直到收到回执 |
| P0 | 文字消息（单聊/群聊/广播） | 支持离线暂存与多跳转发 |
| P0 | 位置共享 + 地图态势 | 队友位置实时刷新，离线地图可用 |
| P0 | 多跳中继 | 任意节点自动转发，扩大覆盖 |
| P1 | 语音消息（录音→分片→传输→播放） | 不是实时通话，体验接近微信语音 |
| P1 | 设备角色与中继选举 | 自动选最优转发节点，带防抖 |
| P1 | 离线地图与坐标纠偏 | WGS84/GCJ-02 处理 |
| P2 | 实时语音（仅局域网/近场） | WebRTC / 对讲式 PTT |
| P2 | 卫星回传（北斗短报文） | 文字回传，分钟级延迟 |
| P2 | 车载/无人机节点 | 高功率、高海拔中继 |
| P3 | 与官方应急系统对接 | 指挥中心数据交换 |

### 1.3 明确不做（v1）

- 不做视频传输（带宽不允许）。
- 不做公网 IM 替代品（有网时优先用现有网络，本平台是"断网兜底"）。
- 不做无授权的频段发射（见第 4 节）。
- 不做"手机之间几公里直连"的承诺（物理上不成立）。

## 2. 传输通道可行性（逐项论证）

| 通道 | 单跳典型距离 | 速率 | 语音 | 手机原生支持 | 法规 | 结论 |
|---|---|---|---|---|---|---|
| BLE 4/5 | 10–50 m（Coded PHY 空旷可达数百米） | 0.1–1 Mbps | 近场可（8–16 kbps Opus） | Android/iOS 均支持，iOS 后台广播受限 | 2.4 GHz 微功率 10 mW，免照 | ✅ 近场组网主力 |
| BLE Mesh（GATT 转发） | 同上，靠多跳 | 低 | 勉强 | 需自研协议，系统不提供 | 同上 | ⚠️ 只适合小范围、低密度 |
| Wi-Fi Direct / Aware | 50–200 m | 数十 Mbps | ✅ 局域网实时语音 | Android 支持；**iOS 不支持**；Aware 机型有限 | 2.4/5 GHz 微功率，免照 | ✅ 近场高带宽（Android） |
| Wi-Fi（普通 AP/CPE） | 100 m–数 km（定向/高增益） | 高 | ✅ | 手机可连 | 2.4/5.8 GHz 微功率 10/25 mW | ✅ 固定中继、指挥所 |
| LoRa（SX1262/SX1276） | 城区 1–3 km；郊区 3–10 km；乡村 10–30 km；山区视距 50–100 km+ | 0.3–37.5 kbps | ❌ 不支持 | 手机无 LoRa，需外接模块（BLE/USB） | 470–510 MHz 仅限计量等特定用途且**不得组网**；433 MHz 10 mW；须用认证模块 | ✅ 广域文字/位置主力，⚠️ 合规坑最深 |
| VHF/UHF 对讲（144/430 MHz） | 1–20 km（视天线/功率） | 窄带语音 | ✅ 模拟语音 | 需外接电台 + 音频线/蓝牙 | **业余无线电操作证书 + 电台执照** | ⚠️ 持照者可用，不能作为大众方案 |
| 北斗三号短报文 | 全球（区域增强） | 单条约 1000 汉字 | ❌ | 需专用模块/终端 + 北斗卡 | 入网许可 + 运营资质 | ⚠️ 唯一的国产卫星文字通道，门槛高 |
| 天通一号 / 海事卫星 | 全球 | 2.4–4 kbps 语音 | ✅ | 需卫星终端 | 卫星地球站许可、资费高 | ⚠️ 指挥层少量配备 |
| 蜂窝 4G/5G | 有基站即有 | 高 | ✅ | ✅ | 正常 | ✅ 有网时优先，作为回退 |
| WebRTC（局域网/公网） | 取决于底层网络 | 高 | ✅ | 浏览器支持 | 无 | ✅ 指挥台与近场实时语音 |

### 2.1 关键物理事实（决定架构，不可绕）

1. **手机本身没有远距离射频能力**。蓝牙/WiFi 是 2.4/5 GHz 微功率，穿墙和绕射能力差；几公里通信必须外接 LoRa/电台/卫星。
2. **LoRa 的带宽只有几百 bps 到几十 kbps**。一条 10 秒的 Opus 语音（16 kbps）约 20 KB，在 LoRa 上要传几十秒到几分钟，且会阻塞全网。所以"LoRa 实时语音"不成立；"LoRa 语音消息"在实验室勉强可行（低码率 Codec2），但不建议作为 v1 承诺。
3. **BLE 的瓶颈不是带宽而是连接数与广播占空比**。一个手机同时维持 7 个 BLE 连接已是上限，密集场景需要"扫描-转发-休眠"调度。
4. **iOS 不允许应用在后台做 BLE 广播（peripheral 模式）**，也不支持 Wi-Fi Direct/Aware。iOS 只能做"前台近场节点"或"连外接 LoRa 模块的终端"。
5. **北斗短报文的延迟是秒级到分钟级**，且是"发→中心→收"的星状链路，不是 mesh；它可以作为"出灾区的最后一跳"，但不能承载实时位置流。

### 2.2 结论矩阵

| 能力 | 近场（<500 m） | 广域（1–30 km） | 无网灾区 |
|---|---|---|---|
| 文字 | ✅ BLE/WiFi | ✅ LoRa（合规前提下） | ✅ |
| 位置 | ✅ | ✅（降频） | ✅ |
| 语音消息 | ✅ | ⚠️ 实验性，不建议 | ⚠️ |
| 实时语音 | ✅ WiFi/BLE | ❌（除非持照电台/卫星） | ⚠️ 仅近场 |
| 求救出灾区 | ✅ | ✅ LoRa 链路 | ⚠️ 北斗短报文 |

## 3. 中国法规与合规（最大的非技术风险）

### 3.1 必须知道的红线

1. **《无线电管理条例》**：任何无线电发射设备须取得**型号核准（SRRC）**；微功率设备符合《微功率短距离无线电发射设备目录和技术要求》（工信部 2019 年第 52 号公告）可免于型号核准，但**频段、功率、带宽、占空比必须逐项符合**，且不得擅自改天线、加功放。
2. **470–510 MHz 的坑**：该频段在微功率目录中限定为**民用无线电计量仪表**等用途，要求**单频点、单次发射 ≤1 秒、不得用于组网**。网上大量"470–510 MHz 免照组网"的说法**不准确**，拿 Meshtastic 直接跑该频段做 mesh 存在合规风险。
3. **433.05–434.79 MHz**：通用无线遥控类，**10 mW (e.r.p)**，同样有占空比/用途限制。低功率下距离只有几百米级。
4. **业余频段（144–148 MHz、430–440 MHz）**：需要**业余无线电操作证书**（A/B/C 类）和**电台执照**，且不得用于商业/营利通信。可以作为"持照救援队"的补充，但不能作为面向公众的产品形态。
5. **卫星**：北斗短报文终端需要**北斗卡（实名）+ 进网许可**；运营服务需要资质（可对接"北斗海聊"等持牌平台）。天通/海事卫星需要卫星地球站相关许可。
6. **无人机/车载**：加装发射设备涉及无人机无线电管理、车载电台管理；大功率设备需审批，不能"自己焊一个 5 W 功放"。

### 3.2 合规结论

- 面向公众的**免照广域 mesh 没有合法通道**。能做的是：**认证微功率模块（BLE/WiFi/LoRa 低功率）+ 限定频段 + 限定功率 + 明确用途**，并接受"城市几百米、郊区数公里"的真实覆盖。
- 想要更远距离，只有三条路：**持照（业余/专用）**、**商业卫星**、**与持牌应急通信运营方合作**。
- 比赛阶段是**原型演示**，用认证模块、小功率、短时发射；**产品化前必须做 SRRC 与合规评估**。这一条要写进 BP，评委反而会加分。

## 4. 必须解决的问题清单

### 4.1 物理与硬件（P0）

- [ ] 手机无远距离射频：必须定义"外接模块"形态（BLE 转 LoRa / USB 转 LoRa）。
- [ ] 模块功耗与续航：LoRa 发射瞬时 100–150 mA，随身节点需 2000 mAh 以上 + 休眠调度。
- [ ] 天线：手持鞭状天线 vs. 车载/无人机高增益天线，效率差 10 倍以上。
- [ ] 多射频共存：BLE + WiFi + LoRa 同时工作时的互调干扰（尤其 2.4 GHz 邻近信道）。
- [ ] 设备发热与防水（户外救援场景）。
- [ ] 硬件成本：每人一套终端的目标 BOM（建议 < ¥300）。

### 4.2 法规与供应链（P0）

- [ ] 频段选择：433 MHz（10 mW）还是申请专用频率/与持牌方合作。
- [ ] 模块 SRRC 认证状态核查（买认证过的模组，不用裸芯片自组）。
- [ ] 北斗短报文的卡、平台、资质路径。
- [ ] 无人机/车载加装的审批边界。
- [ ] 应急场景下的频率协调（与当地无线电管理机构、应急管理部门）。

### 4.3 手机系统限制（P0）

- [ ] Android 后台保活：前台服务 + 电池优化白名单 + 通知常驻。
- [ ] iOS 后台 BLE 广播不可用：iOS 只能"前台中继"或"终端"。
- [ ] Android 12+ 蓝牙权限（BLUETOOTH_SCAN/ADVERTISE/CONNECT）与 Android 13 附近设备权限。
- [ ] Wi-Fi Direct 在部分机型上的兼容性与多跳支持（系统只给单跳，需自研）。
- [ ] Web 端无法做 BLE 广播/外设（Web Bluetooth 只能做 central），Web 只能当"指挥台/模拟器/Web Serial 接模块"。

### 4.4 组网与路由（P0）

- [ ] 邻居发现与链路度量（RSSI/SNR/丢包率/时延/电量/负载）。
- [ ] 中继选举：不能只看"发射功率最高"，要看**链路余量 + 拥塞 + 电量 + 位置**，并加**滞后防抖**。
- [ ] 广播风暴抑制（重复包去重、延迟转发、TTL、按需转发）。
- [ ] 单播路由（AODV 类按需路由）+ 路由失效恢复。
- [ ] 分片与重组（LoRa MTU ~200 B，BLE ~180 B，WiFi ~1200 B）。
- [ ] 优先级队列：SOS > 控制 > 文字 > 位置 > 遥测。
- [ ] 存储转发（断链时缓存，恢复后补发）。
- [ ] 网络分区与合并（两个孤岛相遇后的状态同步）。
- [ ] 环路检测与跳数上限。

### 4.5 语音（P1）

- [ ] 编码：Opus 16–24 kbps（近场） / Codec2 700–1200 bps（LoRa 实验）。
- [ ] 语音消息分片、乱序重组、丢包隐藏。
- [ ] 半双工 PTT 与回声消除（近场实时）。
- [ ] 语音的存储与转发（不能实时时的降级路径）。
- [ ] 带宽预算：一条 10 秒语音会占用 LoRa 信道数十秒，需要"语音配额"。

### 4.6 定位与地图（P0）

- [ ] 无网定位：GPS/北斗冷启动 30–60 秒，室内不可用；需要"最后已知位置 + 惯性推算"。
- [ ] 坐标系：GPS 是 WGS84，高德/腾讯是 GCJ-02，百度是 BD-09；不转换会偏 300–500 米。
- [ ] 离线地图：PMTiles/矢量瓦片，按灾区预下载；存储 50–500 MB。
- [ ] 位置隐私：公共频道只发模糊位置（100 m 网格），精确位置只在队伍加密频道。
- [ ] 海拔/楼层：二维地图不够，需支持高程与"楼层备注"。

### 4.7 安全与信任（P0）

- [ ] 无中心身份：设备自生成密钥对，二维码互加；防止假冒求救。
- [ ] 端到端加密：群组密钥分发（X25519 + HKDF），消息签名（Ed25519）。
- [ ] 防重放：消息 ID + 时间窗。
- [ ] 密钥轮换与成员移除。
- [ ] 滥用防护：限速、黑名单、SOS 防刷。
- [ ] 隐私：位置数据最小化、可撤回。

### 4.8 数据一致性（P1）

- [ ] 离线写入冲突：位置用 LWW（带 Lamport/HLC 时间戳），消息用追加日志。
- [ ] 去重与幂等：同一条消息多路径到达只显示一次。
- [ ] 回执与已读：端到端 ACK，多跳回传。
- [ ] 存储上限与淘汰策略（IndexedDB/SQLite）。

### 4.9 产品与运营（P1）

- [ ] 零学习成本：SOS 一个按钮，地图一眼看懂。
- [ ] 低电量模式：屏幕常暗、位置降频、只收不发。
- [ ] 多语言/大字模式/无障碍（Hack4Good 加分项）。
- [ ] 演练与培训：真实灾害中没人有时间学新 App。
- [ ] 与 110/119/120 的关系：不做替代，做"最后一段"的补充。
- [ ] 责任边界：不能承诺"一定能救到你"，避免法律风险。

### 4.10 测试与验证（P0）

- [ ] 仿真：50–200 节点、丢包 30%、移动模型、分区合并。
- [ ] 实测：2 台手机 + 2 个 LoRa 节点，城区/郊区/山区各测一轮。
- [ ] 压力：SOS 风暴（100 条/分钟）下的时延与成功率。
- [ ] 断电/重启/存储满/时钟错乱等异常。

## 5. 总体架构（防返工设计）

### 5.1 分层

```
┌──────────────────────────────────────────────────────────┐
│ 应用层  App (Web / Android / iOS / Desktop / Embedded)     │
│  SOS · 聊天 · 地图态势 · 语音 · 设置 · 演练模式             │
├──────────────────────────────────────────────────────────┤
│ 会话与同步层  Session / Sync                               │
│  频道 · 成员 · 消息队列 · 回执 · CRDT 位置 · 离线缓存        │
├──────────────────────────────────────────────────────────┤
│ 安全层  Security                                          │
│  设备身份(Ed25519) · 群组密钥(X25519+HKDF) · 签名 · 防重放   │
├──────────────────────────────────────────────────────────┤
│ 组网层  Mesh                                              │
│  邻居表 · 链路度量 · 中继选举 · 广播抑制 · 单播路由 · 分片     │
├──────────────────────────────────────────────────────────┤
│ 传输抽象层  Transport Abstraction (TAL)                    │
│  ┌────────┬────────┬────────┬────────┬────────┬────────┐  │
│  │ BLE    │ WiFi   │ LoRa   │ 北斗    │ WebRTC │ 模拟器  │  │
│  │ GATT   │ Direct │ SX1262 │ 短报文  │ DataCh │ Sim    │  │
│  └────────┴────────┴────────┴────────┴────────┴────────┘  │
├──────────────────────────────────────────────────────────┤
│ 物理层  手机 / 外接模块 / 车载台 / 无人机 / 卫星终端          │
└──────────────────────────────────────────────────────────┘
```

**核心原则：协议先行，传输可插拔。** 上层只认 `Envelope`，不认具体射频；新增一种通道 = 新增一个 adapter，不改业务代码。这是避免推倒重做的关键。

### 5.2 关键设计决策（写入 ADR）

| 决策 | 选择 | 理由 |
|---|---|---|
| 协议编码 | CBOR（二进制，紧凑） | LoRa 上比 JSON 省 40%+ |
| 消息模型 | 不可变信封 + 追加日志 | 多路径去重、易做回执 |
| 位置同步 | LWW-Element-Map + HLC | 无需中心、抗乱序 |
| 身份 | 设备密钥对，ID = 公钥哈希前 8 字节 | 无中心、可离线验证 |
| 群组加密 | 预共享群密钥 + 成员密钥包 | 比 Signal 协议简单，够用 |
| 路由 | 广播洪泛（SOS/位置）+ 按需单播（聊天/语音） | 灾后拓扑变化快，洪泛更鲁棒 |
| 中继选举 | 复合度量 + 滞后 | 只看功率会选出"吵但不可靠"的节点 |
| 语音 | 语音消息优先，实时语音仅近场 | 物理带宽决定 |
| 地图 | MapLibre + PMTiles 离线包 | 开源、可离线、体积可控 |
| 代码共享 | TypeScript 协议内核（Web/RN/桌面复用） + Rust 嵌入式 | 一套协议多端实现 |

### 5.3 仓库结构（monorepo）

```
resqnet/
├─ packages/
│  ├─ protocol/        # 协议内核：Envelope、编解码、分片、去重、HLC
│  ├─ mesh/            # 邻居表、路由、中继选举、广播抑制
│  ├─ crypto/          # 身份、签名、群组密钥
│  ├─ sync/            # 消息队列、回执、位置 CRDT
│  ├─ transport-*/     # ble / wifi / lora / beidou / webrtc / sim
│  └─ ui/              # 共享组件（地图、聊天、SOS）
├─ apps/
│  ├─ web/             # 指挥台 + 演示（比赛交付物）
│  ├─ android/         # 完整功能（BLE 中继）
│  ├─ ios/             # 终端模式（受限）
│  ├─ desktop/         # Tauri + USB 串口接 LoRa
│  └─ embedded/        # ESP32 / 树莓派 固件
├─ sim/                # 多节点仿真器（可视化）
├─ docs/               # 本文件、协议规范、ADR
└─ hardware/           # 硬件选型、接线、外壳
```
