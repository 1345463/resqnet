## 二、作品是什么

**一句话**：给基站瘫痪、断电断网的灾区现场，一个"没有中心服务器也能互通"的应急信息层——手机/中继/车载/无人机自动组网，多跳转发 SOS、文字、位置与语音消息，指挥端用真实地图统一处置。

两个入口：
- **态势演示台**：把多跳路由、广播抑制、中继选举、分片重组做成可点开的可视化
- **管理端**：真实节点台账、事件处置、消息下发，支持 WebSocket 网关接入真实 LoRa 硬件

## 三、为什么做

灾害发生后最常见的不是"没有救援"，而是"不知道谁在哪、谁需要什么"：
- 基站退服、道路中断，公网 IM 直接失效
- 对讲机只能语音，无法形成可检索的台账与位置态势
- 现有 mesh 方案要么必须人人装同一款 App，要么依赖网关/互联网

我们想验证一件事：**在没有任何中心服务器的前提下，普通设备能不能自己把求救信息送到指挥端**。答案是能，但有严格的物理与合规边界（见第五部分）。

## 四、怎么用（5 步）

1. 打开作品链接，选择场景（城区 / 山地 / 震后）
2. 地图或左侧选择一个"居民/队员"节点
3. 点 **SOS 求救**：看红色数据包如何逐跳到达指挥车、指挥车如何回执
4. 断开某个中继，观察网络自动绕行与主中继切换
5. 发一条文字或语音消息，右侧日志显示跳数与端到端时延

管理端（真实台账）：
1. 打开管理端，设置里填网关地址（模拟器 `ws://127.0.0.1:8081/` 或硬件 `ws://<网关IP>:81/`）
2. 节点上线后自动出现在台账与地图
3. SOS 自动生成事件，可"响应/关闭"
4. 选中节点直接下发指令
5. 应急模式下登记呼号、报备编号、频段与功率

## 五、用 Qoder 做出来的过程

> 全程在 Qoder Desktop 中完成，按版本迭代提交到 GitHub。

1. **可行性论证**：把"手机 + 免执照无线电能不能跑实时语音"交给 Qoder 查证，得到关键结论——LoRa 带宽不够、470–510 MHz 不得组网、iOS 后台不能广播；据此砍掉"广域实时语音"，改为"语音消息 + 近场实时语音"。
2. **协议先行**：Qoder 起草帧格式、消息类型、去重/TTL/优先级、中继评分与滞后防抖，形成 `docs/01-协议规范`，后续 Web/固件共用同一套字段。
3. **仿真内核**：Qoder 实现链路预算（距离/遮挡/功率）、广播扩散、SOS 回执与重发；我在浏览器里逐项验收（多跳、断节点绕行、重复包抑制）。
4. **指挥台 UI**：Qoder 生成态势地图、节点面板、传输日志、语音分片进度；我调整了中继箭头、标签避让、手机端比例。
5. **真实管理端**：Qoder 搭出高德底图 + GCJ-02 纠偏、节点台账、事件流转、消息下发、WebSocket 网关协议与本地持久化。
6. **LoRa 网关固件**：Qoder 写 ESP32-S3 + SX1262 固件（LoRa ↔ WebSocket ↔ BLE NUS），我按 B 类证与微功率限值确定 433 MHz/8 dBm 参数，并补了无硬件模拟器。
7. **合规**：把条例第 37 条应急临时设台做成"应急模式"，避免现场漏报。

## 六、技术要点（评委可跳过）

- 传输抽象层：BLE / WiFi / LoRa / APRS / HaLow / 北斗共用一套 Envelope
- 中继选举：SNR、ETX、电量、负载、高度综合评分 + 20% 滞后防抖，避免"只看功率"
- 广播抑制：按得分延迟转发、听到即取消、SRC+SEQ 去重
- 语音：Opus 分片、乱序重组、全部到达后生成语音消息
- 合规边界：433 MHz 10 mW、470–510 MHz 不得组网、B 类 30 MHz 以上 ≤25 W、应急临时设台须报告
